# M2 preparation and stems

M2 is in progress. Persistent source-audio preparation, cancellation and local
library import/list/load are implemented. Beat/phrase/key/cue analysis, cue
import and prepared/live stem mixing remain unfinished. The failed
**4.095-second live-stem service p99** remains a
mandatory M2 release blocker under the
[approved M0 decision](decisions/0002-m0-stem-runtime.md). A prepared-PCM cache
hit does not measure separation performance.

Loading a track prepares stereo 48 kHz float PCM and its waveform off the GUI
thread. The cache key includes the source SHA-256 and preparation recipe,
including decoder/converter versions, format and waveform settings. Reopening
an entry validates its manifest, PCM size, SHA-256, finite samples and waveform
through the retained read-only descriptor. Matching content can reuse an entry
across filenames; changed source content uses a different key.

Preparation hashes and decodes the same opened regular file, then checks its
identity, size, timestamps and content again before returning or publishing.
Complete PCM and metadata are staged and synchronized before publication.
Malformed regular entries are regenerated; unexpected files, symlinks and
FIFOs fail closed. These checks detect ordinary concurrent changes; they do not
provide a snapshot against malicious writes by the same user.

The manual player stores entries under Qt's application cache directory in
`prepared/v1`. On this laptop that is on ext4. Limits are 1 GiB of source
bytes, 256 MiB of prepared PCM per track, 64 entries, 16 KiB per manifest and
2 GiB of managed cache/preparation storage. Publication reserves room for the
anonymous candidate and staged copy as well as existing entries. A full cache
rejects further preparation; this slice does not evict existing tracks.
Filesystem page cache remains separate from the fixed reader buffers.

**CANCEL PREPARATION** remains available until the GUI accepts the result for
installation, including when worker completion is waiting in the event queue.
Cancellation leaves loaded-deck metadata and current playback intact. Loading
stays busy until candidate readers and descriptors are released. Once the
status becomes **Installing**, cancellation is unavailable. A result already
published before cancellation may remain cached for a later load.

The library drawer imports an absolute local-file path and lists saved tracks.
Select a saved row, then use **LOAD A** or **LOAD B**. Editing a path restores
direct loading. Filenames with Unicode, spaces, `#` and `%` retain their literal
meaning; displayed names use plain text. Timing and key analysis remain
unknown. Missing sources are marked from the last library read/import snapshot;
each load rechecks the actual source hash before installing audio. A changed
file must be imported again. Importing identical content at another path updates
its existing row; changed content at the same path replaces that row's identity.

Library metadata lives in `library.json` under Qt's application data directory,
outside the PCM cache. The versioned catalog is bounded to 1 MiB and 1,024
records. Writers lock, reread and merge before an atomic save with private file
permissions. Invalid, oversized, symlink or FIFO catalogs fail closed and remain
untouched. Their error remains visible while direct path loading stays usable.
Source preparation limits still apply to imports.

Import cancellation remains available through queued preparation completion.
The **Saving** phase commits the accepted catalog change and cannot be cancelled;
shutdown joins that write. Catalog startup reads and imports leave active
playback alone. Importing does not load either deck. Cue data and automatic
musical analysis are not populated by this slice.

Tests cover cold/reopened reuse, source changes, corrupt entries, unsafe file
types, storage bounds, concurrent publication and cancellation after a real
source read. Controller and QML tests exercise cancellation state, pointer and
keyboard controls, retained playback controls and installation cutoff. A
private virtual PipeWire check compares generated channel samples while the
peer deck prepares/cancels, verifies cached retry and exercises immediate
shutdown from completion notification. It uses no hardware output and makes
no latency or listening claim. See [testing and coverage](testing.md) for the
commands and measurement limits.

After the normal build, run the cache/controller/UI regressions and private
playback check with a fresh evidence directory:

```sh
ctest --test-dir build/dev --output-on-failure \
  -R '^(prepared-track-store|deck-controller|manual-ui)$'
python3 tools/experiments/private_routing_check.py \
  build/dev/conflux-preparation-controller-check \
  build/preparation-check --functional-only
```

On 18 October, the preparation-cache slice passed **23/23 CTest entries**, the
offscreen smoke, **85 private routing checks** with their normal deadline gates
and **15 private preparation checks** in functional-only mode. The preparation
check observed no incorrect or zero samples on the advancing peer deck, and
both private daemons cleaned up their owned nodes/links and exited. Retained
[verification evidence](benchmarks/data/m2-preparation-2026-10-18/verification.json)
pins the tested source by SHA-256.

The initial cache/controller/UI behavior tests failed before implementation.
Later regressions reproduced deletion of a valid entry under tighter budgets
and a crash when completion triggered immediate shutdown. Both fixes passed
the final checks. Their failing logs/results remain beside the verification
record. These results complete the preparation-cache slice, not M2's musical
analysis or live-stem gates.

The separate instrumented run passed the same CTest suite, smoke and both
private functional suites. It measured **78.13% C++ line coverage** and
**93.03% Python worker line coverage**. The C++ goal remains unmet; QML and the
native stem adapter remain unmeasured. Raw counts and scope are recorded in
the [coverage result](benchmarks/data/m2-preparation-2026-10-18/coverage.json).

The subsequent library slice passed **24/24 normal CTest entries**, the
offscreen smoke and **30 private playback checks**. Those checks exercised

The native runtime now exposes its existing graph upload, compute/synchronize
and readback wall intervals. These measure CPU wall time, not GPU kernel
timestamps. The pinned build overlay adds three fields and three assignments
without changing upstream files, model settings, clocks or synchronization.

A fresh two-thread comparison completed 16 windows in each persistent runtime.
All 16 diagnostic outputs matched the baseline PCM bytes exactly; inputs,
source/artifact pins, phase fields and owned-process cleanup also passed.
This verifies the instrumentation for those windows. Fixed runtime order and
thermal differences prevent a causal timing-overhead or latency claim.

The first 600-second audio/UI diagnostic attempt did not start. During preflight,
43 samples recorded a maximum stable span of 30.699 seconds against the required
60 seconds at or below 55°C with balanced mode and the recovered guard. The
attempt was interrupted when its original readiness window could no longer
accommodate the workload, and its owned child was reaped. The final readiness
proof was not produced before interruption; the trace is retained. There are
no loaded latency, worker-cancellation, audio/UI or thermal-soak results from
that attempt.

The fresh retry completed **600 seconds** with Codex minimized, AC connected and
lid open. Continuous delivery produced 100 chunks: median **1.703 seconds**,
p95 **5.009 seconds**, p99 **5.674 seconds** and maximum **5.844 seconds**.
Fourteen requests missed the strict 4.095-second target. The virtual playback
clock observed no ordinary ready-buffer depletion, but it did not play stems
through the audio probe. This ten-minute diagnostic does not qualify the
required sustained or integrated stem-playback runs.

All delivered requests contained phase measurements. Continuous compute/wait
p99 was **5.373 seconds**, compared with **8.850 ms** upload and **24.774 ms**
readback p99. The worst request spent **5.516 seconds** in compute/wait. These
CPU wall intervals locate the measured tail inside backend graph execution
and waiting; they do not identify individual GPU operations or establish why
the GPU slowed. Low actual GPU clocks relative to requested clocks and firmware
low-power samples remain correlations.

The single cancellation acknowledged supervisor invalidation in **0.106 ms**;
the in-flight request still took **4.956 seconds** to finish. Resumed output
was ready **9.463 seconds** after resume and delivered **14.600 seconds** after
cancellation. Held output was rejected, no stale chunk was delivered and the
trimmed seek matched exactly. Hardware submission was not observed, so this
checks invalidation and recovery rather than GPU preemption.

The independent silent audio probe rendered **112,800 callbacks**, with all six
observed fault counters zero. Callback execution p99 was at most **40 microseconds**
and maximum **594.5 microseconds**. The animated software Harness UI recorded
**18,800 frame notifications**, passed visibility coverage and had a maximum
notification gap of **46.859 ms**. These checks cover audio callback execution
and GUI notifications; they do not measure physical audio/display latency or
normal CDJ stem playback. The two sampled temperature sensors peaked at
**65.05°C** and **87°C**. Four isolated package readings reached 85°C; their
largest capture-conservative bracket was **1.027 seconds**, which describes
sampled excursions rather than continuous temperature or unseen peaks. Owned
processes, window guard and idle inhibitor cleaned up successfully. Raw logs,
derived metrics and measurement limits are retained in the phase-timing
verification record linked above. The live-stem release blocker remains open.


A separate six-request GPU-operation profile completed after normal guard
recovery. All six outputs matched retained PCM hashes exactly, all 32 pins
remained stable and owned resources cleaned up. The native profile took
**10.439 seconds**, with request walls of **1.632–1.745 seconds**; it used two
fixed windows, repeated three times, without UI or audio load. It did not
reproduce the long stall and provides no loaded-service p99 qualification.

Across those deliberately perturbed profiles, half-precision matrix products
accounted for **34.21%** of the printed GPU intervals, softmax **12.19%** and
full-precision matrix products **10.17%**. These intervals include profiler
synchronization/internal work; the shares are not exclusive kernel costs or
predicted savings. An isolated experiment tests the existing Vulkan graph-order
optimizer before allocation. The raw tables, derived categories,
readiness and independent 60-check audit are retained in the same verification
record. No new audio, cancellation or musical-quality result is claimed.


The isolated graph-order candidate builds successfully and passes six source-pin
checks, including rejection of modified inputs. Static review confirms the
single Vulkan optimization call precedes allocation and all seven affected
translation units use the identical timing header. Its pinned overlay and
build record are retained with the evidence. The product runtime has not changed.

A fresh comparison completed **16 baseline and 16 candidate requests**, with all
16 paired PCM outputs matching exactly. The candidate moved **2,849 of 2,941**
graph positions before allocation and reported a **379,841,952-byte** graph
buffer. Per-child peak resident memory was **280,532 KiB** for baseline and
**281,088 KiB** for the candidate; these observations do not measure total GPU
memory, and baseline graph-buffer bytes were not measured.

Request-wall medians were **1.636 seconds** for baseline and **1.806 seconds** for
the candidate, using the arithmetic mean of the two central observations.
Baseline always ran first, and in-run clock and temperature samples were not
retained, so the observed **10.37%** increase does not establish a causal
regression. All source/artifact pins remained stable, the independent audit
passed **38 checks**, and owned children, groups and temporary files cleaned up.
The comparison had no audio/UI or cancellation load and does not qualify the
**4.095-second p99** target. A small counterbalanced comparison will retain every
request and reverse runtime order before another sustained loaded test.
