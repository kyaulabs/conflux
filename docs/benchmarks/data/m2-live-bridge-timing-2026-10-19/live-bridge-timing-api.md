# Live bridge observation API

This fixes the proposed surface in `live-bridge-timing-api.hpp` for root review. It is not frozen for TDD and adds no implementation or test authorization.

The factory creates one `LiveStemObservations` beside its existing `LiveJob`. Its immutable `Setup` contains existing validated identities, exact N/M and four factory milestones. `inputCapturedNs` follows named raw capture, finite scan/hash and source overview; `countCompleteNs` follows the existing exact count pass; `factoryCommittedNs` follows the final source/input/engine/health checks immediately before successful return. These timestamps do not include the controller's prior cache lookup or pool wait. The harness retains its surrounding load-issued interval separately.

Only `PreparedTrackStore` constructs the handle. One private `detail::LiveStemObservationWriter` access struct, defined in `LiveStemBridge.cpp`, writes factory Setup or Bridge records; there is no public writer, subscriber, configurable capacity or clock injection. Setup and queue are different storage: factory may finish Setup while the producer writes records, but no consumer obtains the handle until factory return. Bridge must use existing job/request context and never read Setup during those factory writes. Only the post-publication consumer reads Setup. The existing future/result publication establishes visibility of completed Setup. Factory never writes the queue.

`PreparedLiveStemTrack::observations` is moved into the existing live `PreparedPcm` metadata. The ordinary GUI/control-owner getter `DeckController::liveStemObservations(int deck) const` returns the shared handle for the current live clip, or null for an invalid/unloaded/finite deck. Obtaining it never allocates a new trace or transfers a playback owner. The harness is its sole consumer and retains each returned handle through replacement and shutdown; the controller does not drain it. The handle owns no job/process/files or back-reference, so retaining observations cannot keep inference or disk reservations alive.

Every record has its kind, attempted-record ordinal and a C++ steady-clock observation stamp. All C++ fields ending `Ns` use that same nanosecond domain. Python `workerReadySeconds` and `servicePublishedSeconds` retain their original monotonic-second values; `hopServiceMs` retains milliseconds. No implicit cross-process clock mapping is provided. Invalid clock observations increment a diagnostic error count and cannot become zero-duration measurements. Fields not belonging to the record's kind are ignored, not interpreted as measured zeros.

| Kind | Required meaning beyond ordinal/time |
| --- | --- |
| ServiceReady / RuntimeReady | Receipt of the existing validated ready event. Ready context is still bound by the existing pins/schema; neither event alone proves Flash. |
| RequestObserved | New provider epoch and target48000 in `outputFirst48000`, observed by the producer. Unknown worker generation is not yet assigned. A same-epoch underrun does not emit this kind. |
| CommandQueued / CommandAccepted | Actual load/seek `commandId`, anchor44100 in `inputFirst44100`, target48000 in `outputFirst48000`, provider epoch and, after acceptance, validated worker generation. Queued is sampled just before the successful complete QProcess write; it does not claim kernel-pipe delivery. Do not relabel ACK/close acknowledgements as load/seek. |
| ChunkValidated | Worker generation/request ID/lease sequence, raw44100 range/final; `observedNs` was sampled after complete parsed/schema validation and before lease scanning, `validatedNs` after whole-lease finite/hash/stat checks. Preserve existing service stamps and optional hop metric, using `hopServicePresent`. No successful row is emitted for a rejected lease. |
| PacketAccepted | Matching provider epoch, worker generation and exact output48000 range/final. `packetReadyNs` is the first complete eligible packet; a final packet is eligible only after actual EOF/count proof. `publishBeginNs` and `publishEndNs` bracket the successful `tryPublish` call. `fullObserved` controls whether `firstFullNs` exists. No record is emitted for each retry. |
| PacketDiscarded | Superseded/stopped pending output range and its old epoch, at `observedNs`. It has no accepted-publication or packet-availability interval, including when only a partial packet existed. |
| RawComplete / ConverterComplete / ServiceClosed | Existing independent completion points, relevant generation/epoch and exact final frame coverage. RawComplete/ServiceClosed preserve the supplied service telemetry-loss value with its present flag. Converter completion never implies rendered EOF. |

Accepted packet ranges prove contiguous publication only. They cannot observe a recovery grant being consumed or the gate opening. `serviceRecovery()` remains healthy/terminal only. Report the first published contiguous reserve at the existing clipped threshold; match applied controls and polled source/output clocks for readable/consumed conclusions. Do not invent a new request when an underrun preserves the epoch.

The record queue follows the existing fixed SPSC acquire/release pattern, with one Bridge writer and one harness consumer. Full drops the new observation only. It increments `droppedRecords`, never changes playback health, and never delays publication. Ordinals advance on every attempted record so loss remains visible. Use the existing lock-free integer atomic requirements; do not extract a generic queue. `counters()` loads `producerFinished` with acquire ordering first, then the other atomic counts. If that first load is true, no further observation writes are permitted and those counts are final; sampling while active is advisory because the fields are individually atomic. Reading after producer join also permits final accounting. The flag does not establish OS-thread exit, join or process/group/job cleanup. Existing lifecycle proof remains authoritative.

Drain at most 256 records per harness turn, writing the evidence log off callback. Retain all record kinds and Full waits. Keep queue loss, service telemetry loss and session `snapshotDrops` separate; missing required records make the affected interval incomplete. Drain again after shutdown before recording final counters. Route reuse keeps the same handle and ordinal sequence; a replacement owner has its distinct token/handle. No rendering clock call, callback hook, allocation, mutex, file I/O or measurement queue is added to the callback.

The short diagnostic reports the unchanged strict service-hop p99 target separately from lease-validation and packet-publication intervals. `published_at` precedes `_Wire.emit`, so its difference from worker readiness excludes JSON serialization/output-queue/pipe drain. First positive cursor polling remains a consumption upper bound; stale negative snapshots cannot supply the lower bound. Nothing here claims sustained p99, automatic fallback, physical audio latency or musical quality.
